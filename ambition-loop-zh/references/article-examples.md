# 案例（改编自原文）

这些案例同时也是回归用例：本技能应该给出类似的方案。

## 1. 修崩溃 → 零崩溃（高度 + 先做准备）
- **原始要求：** 修这个崩溃。
- **野心版：** 让应用保持零崩溃。
- **先做准备：** agent 要能拉取崩溃报告，把每个应用版本对应到 git commit，并能使用 Windows、macOS 和 Linux 机器，自己复现和验证修复。
- **裁判：** 崩溃上报工具里每个版本的崩溃率，加上每次修复前后的复现。

## 2. 季度业务复盘 QBR（高度阶梯）
- **第一级：** 把能拿到的数据都交给模型，问这个季度发生了什么变化、为什么、该怎么办，而不是只更新模板里的数字。
- **第二级：** 找出最紧迫的三个决策，给出可能的方向和各自的正反理由。
- **第三级：** 复盘存在的意义，是让管理层尽早发现问题、调配钱和人。设计比季度 PPT 更好的机制，用公司自己的历史证明它能更早发现问题，再与现有复盘并行运行一个季度。
- **裁判：** 历史回测（对已知的过去问题能提前多久发现），加上并行运行的结果。

## 3. 流失分析（深度）
- 用真正的工具：数据库和统计模型，而不是 markdown 表格。
- **挑战既有认知：** "流失是 onboarding 的问题"。试着用原始事件数据复现这个说法。
- **新知识：** 用一年的日志模拟客户，找出谁都还不知道的最早流失信号，并证明它在没见过的数据上有预测力。
- **裁判：** 留出数据上的预测表现，对比事先说明的基线。

## 4. 页面加载 10 秒 → 5 秒（不合理目标）
- **底线：** 5 秒。**野心目标：** 200 毫秒，当作可解。
- **裁判：** profiler 火焰图，以及在固定硬件和网络下的重复实验室测量，报告 p50 和 p95。
- **没达到 200 毫秒时：** 报告真实数字、每种思路带来的收益和剩下的瓶颈。不要把 5 秒改称为目标。

## 5. QBR 的广度团队
- **动词化：** 让忙碌的人在 30 分钟内相信一个因果故事，并在不确定中做出决策。
- **团队：**
  - 分析师：因果分析
  - 记者：找故事、核实来源
  - 编辑：删到只剩决策
  - 动效和音频设计师：需要现场演示时
  - 做空者：像研究空头仓位那样攻击结论
  - 法务会计：对账
- **规则：** 每个成员贡献一种方法，而不是一种口吻。

## 6. 什么时候不拔高（本技能补充）
- "把 README 第 3 行的错别字改掉。" → `照做`。
- "给我一个统计行数的 bash 单行命令，越简单越好。" → `照做`。
- "生产挂了，立刻回滚。" → `照做`。回滚完成后，才可以提议做一次有野心的事后复盘。
